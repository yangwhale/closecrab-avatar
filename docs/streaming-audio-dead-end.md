# 实时喂音频这条路：调查存档

> 状态：**暂停**（2026-09-19）。等上游支持流式音频输入再继续。
> 这份文档是给「将来重新捡起来的人」看的 —— 包括半年后的我自己。
> **先读这一篇，别重新走一遍。**

## 一句话结论

**LiveAvatar 不支持「一边收音频一边出画面」。** 它所谓的实时指的是
**画面生成得快**，不是音频可以流式进。我们在一条上游自己都没验过效果的
代码路径上，花了一天想把口型做对，没做成，而且能证明这条路有硬上限。

## 怎么发现的

Chris 的判词是唯一的验收标准，因为口型这件事**量不准，只能看**
（量法的坑见 [lip-sync.md](lip-sync.md) 里「会骗你的四件事」）。

|---|---|
| `causal_s2v_pipeline.py`（离线） | 没有 |

⇒ **我们大概是唯一在正经用它的人。** 它的音频条件从没被作者按效果验证过。

## 硬上限：0.81

拿「整段一次编码」当标尺（那条已被确认口型 100% 对），逐块比较每个视频帧
对应的音频特征，余弦相似度：

| 做法 | 均值余弦 |
|---|---|
| 上游原版：每 0.48 s 单独编码 | **0.49** |
| 滑动窗口，回看 0.96 s | 0.57 |
| 滑动窗口，回看 1.92 s | 0.61 |
| 滑动窗口，回看 3.84 s | 0.70 |
| 回看 1.92 s ＋预看 0.96 s | 0.80 |
| 回看 3.84 s ＋预看 0.96 s | 0.80 |
| **从头到现在的整段前缀 ＋预看 0.96 s** | **0.81** ← 因果做法的天花板 |

最后一行是重点：**把从会话开始到现在的音频全部喂进去，也只有 0.81。**

原因是 `wav2vec2-large-xlsr-53` 带**全局自注意力** —— 某一刻的特征取决于
整段音频，**包括还没说出口的部分**。因果地重现它在数学上就不可能。

⇒ **调窗口是在 0.8 附近打转，再怎么调都够不着。** 这条路不是没修好，
是有硬上限。

> 复现：`scripts/` 里没留这个台子（它依赖 LiveAvatar 那边的模型），
> 做法是只加载 `AudioEncoder`，用
> `extract_audio_feat_from_array` → `get_audio_embed_bucket_fps` 两步
> 算标尺和各个变体，逐帧算余弦。**注意 `_from_array` 把输入写死 bf16，
> 模型要自己 `.to(torch.bfloat16)`，否则报 dtype 不匹配。**

## 试过的第三条：整句到齐再编码

既然因果够不着，就别因果 —— 等一句说完，整段编码一次（跟离线一模一样），
再按块切片喂。代码还在：`CCA_AUDIO_FEAT=utterance`。

**口型没变好**（Chris：「还是对不上，特别差，跟之前一样」）。
但过程里踩出两个结构性的东西，值得留着：

### 1. 「等音频」顺带是整条流水线的节拍器

第一版一句放完就干等下一句 → **五卡死锁**。py-spy 打出来一目了然：

```
VAE rank        停在 pull_utterance（等下一句）
四个 DiT rank   停在 dist.recv（等 VAE rank 发音频块）
```

上游那个方法叫 `_streaming_encode_next_audio_block_or_random` ——
`_or_random` 这个后缀就是在说「**没音频也得给一块，不能停**」。
我实现了前半句，删了后半句。

⇒ 修法：`pull_utterance(timeout=…)` 超时返回 `None`，调用方立刻喂一块
全零特征继续转。`CCA_FEAT_IDLE_TIMEOUT_S` 默认 0.2 s，**这不是调优旋钮，
是防死锁**。

### 2. 空转就会产生不属于任何一句话的帧

补上节拍器之后，没人说话时那些空转块照样生成画面，**而且照发** ——
实测 **12 s 音频出 57.8 s 视频**，音频按视频节奏放，于是又不同步。

⇒ 修法：一个先进先出队列记「这一块是真是空」，帧按 `frames_per_block`
一组归给它，空的那组扔掉。够用的理由：VAE rank 的循环是「先把这一段的
几块 serve 完，再解码吐这一段的帧」，**同进程、同线程、严格同序**。

> ⚠️ 这正是 2026-09-19 上午删掉的 `av_ledger.py` 干的事。删的判断是
> 「抽干之后对应关系由结构保证，不需要数任何东西」—— 在**当时的约束下
> 是对的**，因为不说话时管线是停的。utterance 模式让那个前提不成立了。
>
> **教训不是不该删，是删之前没写下「这个不变量靠什么前提成立」。**
> 这次只装回真正需要的 3 行，没把 324 行搬回来。

## 速度：离线那条也追不上播放

官方五卡脚本（`infinite_inference_multi_gpu.sh`，4 DiT ＋ VAE 并行，
fp8，720×400，4 步），30 s 音频：

| | 耗时 |
|---|---|
| 第一遍（冷） | 115 s |
| 第二遍（热） | **106 s** |

只差 9 s ⇒ **`torch.compile` 不是大头，106 s 就是真实速度。**

- 750 帧 / 106 s = **7.1 fps** = 实时的 **0.28 倍**
- 一段 48 帧（1.92 s 画面）要 **6.8 s**

⇒ 它**确实**一段一段往外吐（`generate()` 里每段 `vae.decode` 完就
`out.append`，最后才 `torch.cat` 返回，改成边解边吐很容易），
**但吐得比播得慢 3.6 倍**，边生成边播撑不住。只能「先渲染完再播」：
一个 30 s 的回答等约 1 分 46 秒。

### ⭐ 没试完的那个口子

**我们自己那条实时管线在同样五张卡上约 20 fps，比这个快近三倍，参数一样。**
说明离线这条没优化过。`causal_s2v_pipeline.py` 里有个现成开关：

```python
_k = int(os.environ.get('LA_TRIM_K', '0'))
_hist = motion_latents[:, :, -_k:] if _k > 0 else motion_latents
```

注释写着「只喂必要的历史 latent，输出只取 `[-infer_frames:]`，全量历史里
绝大部分解完就被丢弃」。**默认是关的。** 如果瓶颈在 VAE 解码全量历史上，
打开可能直接快一大截 —— 这决定了「等一分半」还是「等半分钟」。

**重新捡起来时第一件事试这个，成本 5 分钟。**

## 顺带挖到的真 bug（还没修）

**换形象会把生成搞崩，只要 `torch.compile` 开着就必挂。**

换脸要清注意力缓存（`self.kv_cache1 = None`，防止两个人融在一起 ——
2026-09-18 那次「兔子耳朵长到人手上」就是没清）。但缓存一清，
dynamo 拿着 0 长度张量重新编译：

```
RuntimeError: cannot reshape tensor of 0 elements into shape [0, 40, -1, 2]
```

整条 `_run` 退化成「只出声」，rank 0 跟着死。
**生产影响：用户中途换形象 → 画面没了只剩声音。**

绕开办法：用启动参数 `--image` 定脸，不走中途切换。

## 什么时候重新捡起来

盯上游这一条：**`causal_s2v_pipeline_tpp_blockwise.py` 有没有出现在
某个正式的出片脚本里**（不是 `stream_bench.py`）。出现了，说明作者开始
按效果维护它，那时再谈。

在那之前，要做数字人就走「整段音频 → 离线渲染 → 播」，
并且先把 `LA_TRIM_K` 那个口子试掉。
