# 为什么是这个架构

## 一句话

**控制面记账，worker 干活，worker 主动来拿活。**

```
Agent（任意机器）
 │  AvatarSession(...).start()  ── Bearer JWT
 ▼
控制面（常驻 CPU 小机器，无 GPU）
 │  鉴权 / 调度 / 铸票 / 回收 · SQLite 单文件
 ▲  ← worker 主动连上来（pull）
 │
Worker × N（GPU 机器，一卡一进程，模型常驻）
```

## 三个决定

### worker 是 pull 不是 push

GPU 机器**不需要对外开端口**，可以待在 NAT / 不同 VPC / 不同云后面；
Spot 被回收后换台机器重新注册即可。控制面从不主动连 worker。

代价：worker 要长轮询。换来的是**部署自由度**——这在 Spot 上是刚需。

### 控制面单独放 CPU 机器

GPU 机器（尤其 Spot）会消失，控制面不能跟着消失。
而且控制面**不在媒体路径上** —— 只在建/停会话时被调用一次，放哪儿都不影响帧率。

同机部署完全可以（`--role all`），分开只是为了让控制面活得比 GPU 久。

### 状态用 SQLite 单文件

单实例够用、零外部依赖、重启不丢。要多实例再换 Postgres——
只需要替换 `store.py`，其余不动。

**不要为了「以后可能要扩」提前上 Postgres**：多一个要运维的东西，
而单控制面能扛的会话数远超 GPU 能扛的。

## 一卡一路，不是五卡一路

实测**每卡效率：单卡 1.357× vs 5 卡 0.337×，差 4.0 倍**。
同样 8 张卡，跑 8 路独立会话 ≫ 跑 1 路快 5 倍。

5 卡 TPP 只在「单路要最高画质/最低延迟」时才划算 —— 它是启动受限，
DiT 一次前向 26,617 个 kernel，不随分辨率变，所以分辨率涨了几乎不额外收费。

## 纯逻辑与 I/O 分开

```
avatar_policy.py / audio_stream.py    纯算术，不碰网络，能离线穷举
avatar_link.py / live_generator.py    接线：读房间、探网关、驱动模型
```

这么切**不是为了「可扩展」**（只会有一个实现），是为了**能在没有 GPU 的
机器上把判断逻辑钉死**。音频块调度、打断语义、状态合成这些地方错了都是
**静默错误** —— 视频照出，只是口型对不上、或者打断后还在动嘴。

`audio_feat.py` 是这条原则收益最大的一处：整个「第 *i* 帧视频该对第几毫秒的
声音」是纯算术，23 条测试不用 torch、不用模型、0.14 秒跑完，而它守的那个
缺陷**在真机上只能靠人眼判**。推导和实测见 [lip-sync.md](lip-sync.md)。

判据：拆开如果是为了可离线测，那是承重的；只是「当时顺手」，就该合。
