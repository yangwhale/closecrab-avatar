### 覆盖了什么

| 维度 | 取值 |
|---|---|
| 预热帧数 | 0 / 1 / 5 / 11 / 12 / 13 / 47 / 1000 |
| 流水线深度（块比帧早多少） | 1 / 2 / 3 / 5 / 8 / 20 块 |
| 句尾落点 | 块内第 0…12 帧，逐个试 |
| 打断时块内帧数 | 0 / 1 / 6 / 12；另有连打 50 次 |
| 背压容量 | 1 / 2 / 3 / 6 / 64 块 |
| 消费节奏 | 每 1 / 2 / 7 块取一次 |
| 每块帧数 | 1 / 2 / 3 / 12 / 25 / 100 |
| 随机序列 | 300 条，每条 400 个随机操作 |
| 长跑 | 50 000 块 ≈ **6.7 小时**语音 |

### 四条不变量（每项都验）

    ① 对账平      seen == 预热 + 拒收 + 丢掉 + 已发 + 在途
    ② 配对正确    每块拿到的是它自己那几帧，一帧不错
    ③ 顺序守恒    发布顺序 == 拉取顺序，同一块不重复发
    ④ 不吞错误    该报的都报了（比计数，不看日志文本）

### ⭐ fuzz 第一轮就抓到一个真漏洞

**被拒收的帧计进了 `frames_seen`，对账等式里却没有它的位置。**
后果：只要报过一次「多出来的帧」，`reconciled` 就**永远**为假。

一个报过错之后再也不会变绿的指标，跟一个永远绿的指标一样没用 ——
而对账是「配对还可不可信」的唯一依据。300 条随机序列全红，一眼看见。

补了 `frames_rejected` 这一项之后 357 项全过。

### 另一个发现：我的用例自己写错了

「先拉 8 / 20 块再一次性喂满」一开始也红。**不是账本的错** ——
默认容量 6 块，拉 8 块必然触发背压，那测到的是背压不是深流水。
给足容量后通过。

> 用例写错和实现写错，**红起来长得一模一样**。所以每条红都要先问
> 「我想测的到底是什么」，再去改实现。
