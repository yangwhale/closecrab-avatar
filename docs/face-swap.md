# 换脸：正确的做法，以及三条已经撞过墙的路

> 2026-09-18。这份文档的目的不是记录「我们做了什么」，是**阻止下一个人
> （很可能是我自己）把那三条路再走一遍**。

## 结论先说

**改上游 `generate()`，在轮次开头就地重算参考图那几个张量。**
不退出生成器、不重开循环、不重启进程。

上游文件：`liveavatar/models/wan/causal_s2v_pipeline_tpp_blockwise.py`

要改的位置是外层 `for r in range(active_nr)` 的**开头** —— 那一段五个 rank
都会走到，没有按 rank 分叉。参考图相关的张量（编码后的 latent、初始运动帧）
就是在 Step 1 里算出来的，其中 `self.vae.encode(...)` 这一步所有 rank 都执行。

所以在那儿加一个检查：图变了就重算这几个张量，然后照常往下跑。
五个 rank 走的是**同一行代码**，天然一致，不需要任何额外通信。

代价接近零 —— 省掉的正是「重新进入 `generate()`」那一整套准备工作，
而那套里绝大部分（加载权重、合 LoRA、转 FP8、编译）跟换图毫无关系。

**改法要求**：不直接改上游仓库，走独立补丁文件，免得上游更新时冲突。

## 为什么不是别的做法

换脸 = 换参考图。难点从来不是「换图」，是**这个模型跑在五个咬合的进程上**：
rank 0→1→2→3→4 逐块传张量，谁先跳出循环，剩下的就永远堵在 `dist.recv`
上 —— 不报错，静默死掉。所以任何「中途改变控制流」的方案，都必须保证
五个 rank 在**同一个点**做出**同一个决定**。

下面三条都栽在这一点上。

### ✗ 一、每块在默认通信组里广播一个标志位

上游自己在默认组里就有一对**不对称**的 broadcast：

    DiT rank   在 r==0 / r==1 的轮次开头收
    VAE rank   在 r==0 最后一个 block 发

同一个组里不同 rank 在完全不同的位置发起集合通信，全靠「组内按发起顺序
配对」才对得上。再插一个「每块一次」的 broadcast 会跟它们抢配对：
轻则读到别人的张量，重则死等。

### ✗ 二、另建一个 `dist.new_group()`

NCCL 直接拒绝：

    NCCL WARN Duplicate GPU detected : rank 0 and rank 4 both on CUDA device 8f000
    NCCL error ... invalid usage

先 `torch.cuda.set_device(LOCAL_RANK)` 也没救回来。而且**它不是可捕获的
Python 异常**，`try/except` 拦不住，直接打死一个 rank。

### ✗ 三、按块计数 + 读共享文件（零协调）

思路是把「决定」和「内容」拆开：何时重开用纯块计数（各数各的，天然一致），
用哪张脸读同一个文件。能跑起来，但两个问题：

1. **重入本身很贵。** 实测 3.4 秒/次（17.7 秒音频里重入 3 次，出帧
   444 → 188，帧率 22.1 → 18.3）。我原先估「约 1 秒」，**没测过**。
2. **文件刚被改写那一瞬间，各 rank 可能读到不同的值** —— 有的决定重开、
   有的不重开，决策分歧。而那一刻恰恰是唯一要紧的时刻。
   实测一次会话里触发 5 次重开，服务基本耗在重启上，用户侧表现是
   「第二次重播什么都出不来」。

### ✗ 四、杀进程重启（换 `--image` 重跑）

能工作，也确实简单，但要 3~4 分钟 —— 那是重新加载 47 GB 权重 + 合 LoRA +
转 FP8 + 编译的时间，**跟换图完全无关**。权重常驻、按请求重入本来就是
推理引擎该有的样子，不该为了换张图把它们全扔了。

## 教训

**「不能改上游」这个前提是我自己加的，没人给过我。**
三条路的复杂度全花在「怎么在不改它的情况下绕过去」上。一旦允许改上游，
正确答案比其中任何一条都简单。

其余几条：

- **「这一步很便宜」必须有测量。** 我连说三次「秒级」都没量过，
  而那个数字正是「多久重开一次」的唯一依据。
- **为了避开协调而把不确定性挪走，它不会消失，只会换个更难观察的地方。**
  依次挪到了：通信组配对顺序 → 块计数 → 文件读写竞态。
- **「最坏只是内容不一致」这种风险评估要往严处想。** 我把文件竞态写成
  「最坏一个周期脸不一致」，实际后果是**决策分歧**，严重得多。
