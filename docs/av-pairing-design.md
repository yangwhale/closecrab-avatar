# 音画按序号配对 —— 设计文档

> 状态：**设计，未实现**。2026-09-19。
> 先有这份文档再动代码，是 Chris 的要求，理由见最后一节。

## 要解决什么

一句话：**现在这条链上，没有任何地方记录过「这一帧画的是哪一段声音」。**

生成器吐的是裸张量，队列里是裸张量，发布时按「已发出去几秒音频 / 几秒视频」
配平。秒数可以完全对得上而对应关系完全错，**而且不报错**。

实测后果：同一台机器、同一份代码、同样的三句会话结构，跑两遍，
第二句的音画偏移一次 −20 ms、一次 +1940 ms。
⇒ **不可能用一个固定延迟补偿它。** 详见 [lip-sync.md](lip-sync.md)。

> Chris 2026-09-19：「肯定得有一个 sequence number，告诉你这个音频帧是第几个、
> 它对应的视频帧什么时候出来。他俩带着那个号就能对齐，这就是同步必须的东西。」

## 为什么官方没这个问题

官方那条是**批量**：整段音频进去、一堆帧出来，然后
`merge_video_audio(视频, 音频)` 把生成的视频和**原始那个音频文件**都从 0 开始
合一下，按短的截断。第 *i* 帧天然对应音频第 *i*/fps 秒 ——
**数组下标本身就是序号**，对应关系是白送的。

流式把这个白送的下标弄丢了：上游的 blockwise pipeline **只吐帧、从不吐音频**
（`yield image.cpu()`，没有任何标识）。谁把音频和帧凑到一起送出去，
谁就得自己维护对应关系。这件事一直没人做。

## 接口：**只进音频，只出成对的音视频**。序号不外露

> Chris 2026-09-19：「这个事分两个地方去管理实在是太恶心了。……我本地那个
> 音频帧扔给你以后就不要了，我就等着你给我音频加视频一块出来。」

对。上一版我把 `(utt, blk, i)` 写成了要在接口上传递的东西 —— 那是设计错了，
等于把内部账本摊给调用方，两边都得记、两边都可能记错。

**新接口只有两件事：**

    push(pcm)                 把音频交出去，交完就不管了
    async for av in source:   拿回来的每一项，音频和画面**已经是配好对的**

`av` 里既有这一段音频、也有它对应的那几帧。调用方**看不到任何序号** ——
号只在 closecrab-avatar 内部用于对账，不出边界。

三个端点本来就全在我们这儿（要音频的回调、帧队列、发布循环），
所以这层收口不需要上游配合，也不需要调用方配合。

## ⭐ 这个接口不用我们发明 —— 官方契约本来就是这个形状

`livekit.agents.voice.avatar._types.VideoGenerator`，**供应商要实现的那个抽象类**：

```python
class VideoGenerator(ABC):
    async def push_audio(frame: rtc.AudioFrame | AudioSegmentEnd) -> None
    def clear_buffer(self) -> None
    def __aiter__() -> AsyncIterator[rtc.VideoFrame | rtc.AudioFrame | AudioSegmentEnd]
```

看第三行的返回类型：**迭代出来的既有 `VideoFrame` 也有 `AudioFrame`。**
官方要求供应商**把音频自己重新吐出来**，跟它生成的画面交错在同一条流里。

⇒ **配对靠的是「这条流里的先后顺序」，官方协议里没有序号。**
⇒ 我们的 `LiveGenerator` 本来就实现的是这个接口。**所以这不是要新造一套 API，
   是把已有契约实现对** —— 现在交错的顺序是按「已发出几秒」决定的，
   该按「这几帧是哪块音频生成的」决定。

内部仍然需要账本（下面那节），但它**只用于决定交错顺序**，不外露。
这跟 Chris 要的「我扔进去就不管，你把配好对的还我」是同一件事。

## 不变量（内部）

**每一帧和每一块音频，内部都带同一个身份：`(utt, blk, i)`**

    utt   第几句（`AudioSegmentEnd` 划界）
    blk   这句里的第几块音频（一块 = infer_frames 帧 = 0.48 s）
    i     块内第几帧，0 ≤ i < infer_frames

**成对才出**：第 blk 块的音频和它那 `infer_frames` 帧一起交出去，
帧没齐就不出。不看时间戳、不看秒数。

## ⚠️ 为什么不能「只发一条带声音的视频轨」

> Chris：「LiveKit 那边难道非得音视频拆开来给吗？正常难道不应该是视频里
> 就带着声吗？我只给视频帧就行了，为啥非得增加复杂度？」

**不能，而且这不是 LiveKit 的选择，是实时传输本身的形态。**
「视频里带着声」是容器格式（mp4/mkv）的概念，WebRTC 里没有这个东西：
音频和视频永远是两条独立的流 —— 编解码不同、打包不同、抖动缓冲各一套；
拥塞时先丢视频保音频；订阅方也可能只要声音不要画面。

接收端靠 RTP 时间戳把两条重新对上，这套机制本身是好的（全世界的视频通话
都靠它）。**我们的问题不是它对不上，是我们递给它的那一对本来就不对应** ——
它于是忠实地把错的一对同步得很好。

而且连「给两边盖同一个时间戳」这条捷径也没有，实测 API：

| | 能不能带时间戳 |
|---|---|
| `VideoSource.capture_frame` | 可以（`timestamp_us`） |
| `AudioSource.capture_frame` | **没有这个参数** |
| `AVSynchronizer.push` 的 `timestamp` | 注释写着 **"for logging purposes for now"**，不参与同步 |

⇒ 唯一的杠杆是**在同一时刻递交配好对的一对**，让到达顺序自己成为时间戳。
这正是现在那段代码想做的事，只是它按「秒数」配对，该按「身份」配对。

**结论：复杂度消不掉，但可以全部关在 closecrab-avatar 里，一点不外露。**

## 号从哪来（不用改上游）

两个事实凑起来就够：

1. **`PcmInbox.pull_block()` 是我们自己的回调** —— 模型每要一块，
   我们就知道「第 blk 块被吃掉了」。
2. **一次回调恰好产 `infer_frames` 帧**（当前 12）。

⇒ 回调返回 blk 之后产出的前 `infer_frames` 帧，就是 blk 的帧。

实现形态：

    pull_block()   把 blk 压进一个 FIFO，连同它的 PCM 一起登记
    帧产出侧       维护「当前 blk + 块内计数」，计满 infer_frames 就弹下一个 blk
    发布侧         按 (utt, blk) 取一对，成对交给 LiveKit

### ⚠️ 第 2 条是**假设**，必须当场校验，不能信

这是整个方案唯一的脆弱点，也正是 Chris 担心的「时间长了会错开」的来源：
**一旦某次回调产出的帧数不等于 `infer_frames`，之后所有的号就永久错位一格。**

所以：

- 每块产出的帧数**逐块断言**。不等于 `infer_frames` 立刻记 ERROR。
- **不许静默修正。** 错位必须要么被挡住、要么被吼出来 ——
  今天这条链上所有的坑，共同点都是「不报错地把错误往下传」。

## 丢帧必须成对，而且按块丢

现在队列满了丢**最旧的一帧**，没日志没计数（`_offer`）。
丢帧本身是对的 —— 数字人只有「现在」有意义，补播两秒前的嘴型比丢帧更糟。
**错的是只丢视频不丢音频**：每丢一帧，对应关系就永久错开一帧，
而秒数配平会自动把它"重新平衡"，等于**把错位藏起来**。

改成：

- **按块丢，不按帧丢。** 丢就丢整整一块（帧 + 对应的那段音频）。
  这样边界永远落在块上，对账是整数运算，没有半块状态。
- **丢了要计数、要打日志。** 丢帧是持续性退化，不是偶发，不能去重压成一条。

## 怎么发现漂移（Chris 最担心的那条）

计数类方案的通病：**误差只累积、不自愈**。所以对账必须是常设的，不是排障时才跑。

    每 N 块对一次账：   已消费块数 × infer_frames
                      == 已产出帧数 + 已丢帧数
    对不上            记 ERROR，丢掉在途的，从下一个块边界重新起算

再暴露一个可观测量：**当前对账偏差（帧）**。它必须能被看见 ——

> ⚠️ 现有那个「音频最多领先 0 ms」的监控是**反面教材**：它数的是发出去几秒
> 音频、几秒视频，两个数相等就报 0，根本不看对应关系。**量错了对象，
> 所以永远是绿的。** 新指标要量的是 `(utt, blk)` 对不对得上，不是秒数。

句子边界（`AudioSegmentEnd`）是天然的对账点和重置点：一句说完，
在途的必然清空，此时偏差应当为 0，不为 0 就是有东西漏了。

## 为什么复杂度能包在 closecrab-avatar 里

能。**两个端点都是我们的**：

| 需要什么 | 谁提供 |
|---|---|
| 知道「第 blk 块被消费了」 | `PcmInbox.pull_block()` —— 我们的回调 |
| 知道「这一帧产出了」 | `LiveAvatarPipelineSource` 的帧队列 —— 我们的 |
| 把成对的东西发出去 | `LiveGenerator` 的发布循环 —— 我们的 |

对上游的要求只有一条：**一次回调恰好产 `infer_frames` 帧**。
而这一条我们能在自己这侧断言检查 —— 不需要上游改一行代码，
也不需要上游承诺什么。

## 不选另一条路的理由

「每句话调一次生成器、处理完就退出」（＝把批量那套搬过来）也能对齐，但：

- 五个 rank 靠互相收发**逐块咬合**前进，**中途谁退出，别人就永远卡在接收上**。
  要支持「说完就退、下次再起」得先发明一套五卡停机协议 —— 现在没有。
- 每次重起，模型拿**参考图当起始姿态**（`motion_latents = ref_pixel_values...`）。
  连续对话里每句开头脸会弹回参考姿势，很显眼。
- 还要重付预热（第 0、1 轮用预置音频）。

按序号配对改动集中在两处、不需要停机协议、不会让脸每句一跳。

## 怎么验

**纯逻辑（不要 GPU）**：假回调 + 假帧源

- 正常流：`(utt, blk)` 配对正确，发布顺序与消费顺序一致
- 某块多产/少产一帧 → **必须报 ERROR**，不许静默修正
- 队列满 → 帧和音频**成对**消失，对账仍然平
- 句子边界处偏差归零

**端到端**：脉冲串 —— 每 1.2 s 一个「趴」，中间全静音，跑 8 个。
量每个脉冲的嘴响应位置，**8 个点应当一致**；不一致就是在漂。

⚠️ **每个结论至少跑两遍。** 2026-09-19 在这个话题上我连着错两次，
两次都是样本的变化维度没覆盖真正的自变量 —— 一次拿六个共享盲区的变量
当交叉验证，一次拿一趟干净的运行当定案，复跑就翻。
