# 音画配对 —— 设计文档

> 状态：**设计完成，实现中**。2026-09-19。

## 问题

**这条链上没有任何地方记录过「这一帧画的是哪一段声音」。**

上游生成器吐的是裸张量，队列里是裸张量，发布时按「已发出几秒音频 / 几秒视频」
配平。秒数可以完全对得上而对应关系完全错，**而且不报错**。

实测后果：同机、同码、同样的三句会话结构，跑两遍，第二句的音画偏移
一次 −20 ms、一次 +1940 ms。⇒ **不可能用一个固定延迟补偿。**
（量法与数据见 [lip-sync.md](lip-sync.md)）

### 为什么官方那条没这个毛病

官方是**批量**：整段音频进、一堆帧出，然后把生成的视频和**原始音频文件**
都从 0 开始合一下。第 *i* 帧天然对应音频第 *i*/fps 秒 ——
**数组下标本身就是序号**，对应关系是白送的。

流式把这个白送的下标弄丢了：上游 blockwise pipeline **只吐帧、从不吐音频**。
谁把音频和帧凑一起送出去，谁就得自己维护对应关系。

## 目标接口

**官方契约本来就是这个形状**，不需要我们发明。
`livekit.agents.voice.avatar._types.VideoGenerator`：

```python
class VideoGenerator(ABC):
    async def push_audio(frame: rtc.AudioFrame | AudioSegmentEnd) -> None
    def clear_buffer(self) -> None
    def __aiter__() -> AsyncIterator[rtc.VideoFrame | rtc.AudioFrame | AudioSegmentEnd]
```

迭代出来的**既有视频帧也有音频帧** —— 官方要求生成器把音频**自己重新吐出来**，
跟它生成的画面交错在同一条流里。

⇒ **配对靠的是这条流里的先后顺序，协议里没有序号。**
⇒ 调用方只做两件事：把音频交出去、迭代拿回配好对的东西。**看不到任何编号。**

我们的 `LiveGenerator` 实现的就是这个接口。**所以这不是新造 API，
是把已有契约实现对**：交错顺序现在按「已发几秒」决定，该按「这几帧是
哪块音频生成的」决定。

### 为什么不能只发一条带声音的轨

「视频里带着声」是容器格式（mp4/mkv）的概念，**WebRTC 里没有这个东西**：
音视频永远两条流 —— 编解码不同、打包不同、抖动缓冲各一套；拥塞先丢视频保音频；
订阅方可能只要声音。接收端靠 RTP 时间戳重新对上，**那套机制本身是好的**。

我们的问题不是它对不上，是**递给它的那一对本来就不对应**，
它于是忠实地把错的一对同步得很好。

连「给两边盖同一个时间戳」的捷径也没有：

| | 能带时间戳吗 |
|---|---|
| `VideoSource.capture_frame` | 可以（`timestamp_us`） |
| `AudioSource.capture_frame` | **没有这个参数** |
| `AVSynchronizer.push` 的 `timestamp` | 注释写着 "for logging purposes for now"，不参与同步 |

⇒ 唯一杠杆是**在同一时刻递交配好对的一对**，让到达顺序成为时间戳。

## 内部机制

### 账本

内部给每块音频一个号 `blk`，给每帧记它属于哪个 `blk`。
**号不出边界**，只用来决定交错顺序。

号从哪来 —— 两个事实凑起来就够：

1. **`PcmInbox.pull_block()` 是我们自己的回调**：模型每要一块，我们就知道
   「第 blk 块被吃掉了」。
2. **一次回调恰好产 `infer_frames` 帧**（当前 12，= 0.48 s）。

⇒ 回调返回 blk 之后产出的前 `infer_frames` 帧，就是 blk 的帧。

### ⚠️ 第 2 条是假设，必须逐块校验

**整个方案唯一的脆弱点。** 一旦某次产出的帧数不等于 `infer_frames`，
之后所有的号永久错位一格 —— 而且会悄悄错下去。

- 每块产出帧数**逐块断言**，不等就记 ERROR。
- **不许静默修正。** 这条链上所有的坑，共同点都是「不报错地把错误往下传」。

### 丢帧必须成对，而且按块丢

丢帧本身是对的 —— 数字人只有「现在」有意义，补播两秒前的嘴型比丢帧更糟。
**错的是只丢视频不丢音频**：每丢一帧对应关系就永久错开一帧，
而秒数配平会自动"重新平衡"，等于**把错位藏起来**。

- **按块丢**：丢就丢整块（帧 + 它那段音频）。边界永远落在块上，对账是整数运算。
- **丢了要计数、要打日志。** 这是持续性退化不是偶发，不能去重压成一条。

### 怎么发现漂移

计数类方案的通病是**误差只累积、不自愈**，所以对账必须常设：

    已消费块数 × infer_frames  ==  已产出帧数 + 已丢帧数
    对不上 → ERROR，丢掉在途的，从下一个块边界重新起算

句子边界（`AudioSegmentEnd`）是天然对账点：一句说完在途必然清空，
此时偏差应为 0，不为 0 就是有东西漏了。

> ⚠️ 现有那个「音频最多领先 0 ms」的监控是**反面教材**：它数的是发出去几秒
> 音频、几秒视频，相等就报 0，根本不看对应关系。**量错了对象，所以永远是绿的。**
> 新指标要量「这一块的音频和它的帧对上没有」，不是秒数 —— 否则就是再造一个
> 只会亮绿灯的东西。

## 换形象：生成器从头开始

> Chris 2026-09-19：「换图片这个事情就把 generate 停了，不能再续上，
> 直接从头开始，不要任何 workaround —— 省得上下文污染。」

**这个要求已经满足了**，而且不靠重启进程。`scripts/patch-upstream-faceswap.py`
在换图那一轮把旧形象派生的东西**全部重算**：`ref_pixel_values`、`ref_latents`、
`motion_latents`、`videos_last_frames`，并且 **`self.kv_cache1 = None`**
（注意力缓存和 crossattn 缓存由同一个 `if` 管，一起重建）。

清缓存这条是踩出来的：只换参考图的话缓存里还装着上一个人的注意力状态，
模型会把两个人**融**起来 —— 2026-09-18 实测从兔子换成一张自拍，
生成出来是那个人举着手、**手上长着兔耳朵**。

代价是时序上下文断一次、画面跳切一下。**换人本来就该跳切。**

### 账本要配合两件事

1. **在途的全扔** —— 那些帧是旧脸画的，配新音频就是张冠李戴。
2. **重新进入预热态** —— 上游重启后会再用预置音频跑几轮。

第 2 条是 Chris 提这个 case 时才发现的**真 bug**：账本第一版把「是不是预热」
写成 `blocks_pulled == 0`，而换形象时它早就不是 0 了 ——
于是新一轮预热帧全被判成「多出来的帧」，一路狂报 ERROR。
**假警报会把真警报淹掉，比不报还糟。**

接口：`AVLedger.on_generator_restart(why)`。块号照旧不重置。

## 为什么复杂度能全关在这个仓库里

三个端点全是我们的：

| 需要什么 | 谁提供 |
|---|---|
| 知道「第 blk 块被消费了」 | `PcmInbox.pull_block()` |
| 知道「这一帧产出了」 | `LiveAvatarPipelineSource` 的帧队列 |
| 把成对的东西发出去 | `LiveGenerator.__aiter__` |

对上游只有一条要求：**一次回调恰好产 `infer_frames` 帧**，
而这条我们能在自己这侧断言。**不需要上游改一行，也不需要调用方配合。**

## 不选「每句重调一次生成器」的理由

那条（＝把批量那套搬过来）也能对齐，但：

- 五个 rank 靠互相收发**逐块咬合**前进，**中途谁退出别人就永远卡在接收上**。
  要支持「说完就退、下次再起」得先发明一套五卡停机协议 —— 现在没有。
- 每次重起，模型拿**参考图当起始姿态**，连续对话里每句开头脸会弹回去，很显眼。
- 还要重付预热（第 0、1 轮用预置音频）。

## 验收

**纯逻辑（不要 GPU）**

- 正常流：配对正确，发布顺序与消费顺序一致
- 某块多产/少产一帧 → **必须报错**，不许静默修正
- 队列满 → 帧和音频**成对**消失，对账仍然平
- 句子边界处偏差归零
- **换形象**：在途的旧脸帧被扔、新一轮预热帧不报错、块号仍单调

**端到端**：脉冲串 —— 每 1.2 s 一个「趴」，中间全静音，8 个。
量每个脉冲的嘴响应位置，**8 个点应当一致**；不一致就是在漂。

> ⚠️ **每个结论至少跑两遍。** 2026-09-19 在这个话题上连着错两次，
> 两次都是样本的变化维度没覆盖真正的自变量：一次拿六个共享盲区的变量
> 当交叉验证，一次拿一趟干净的运行当定案 —— 复跑就翻。
